# Testing moderno con Vitest, MSW y Testing Library (sin dolor)

**Subtítulo:**
Cómo construir una estrategia de testing rápida, mantenible y que no te haga odiar los tests.

---

## Introducción

Durante años he visto proyectos donde escribir un test era más difícil que desarrollar la propia funcionalidad.

Mocks imposibles de entender, tests acoplados a la implementación, tiempos de ejecución eternos y suites que fallaban "porque sí".

Cuando empecé a trabajar con **Vitest**, **Testing Library** y **MSW**, entendí que el problema no eran las herramientas. Era cómo las estábamos utilizando.

En este artículo comparto la estrategia que utilizo actualmente para mantener una suite de tests rápida, fiable y sencilla de mantener.

---

# El objetivo no es tener cobertura

Una de las mayores confusiones es pensar que:

> Más cobertura = Más calidad

No.

Puedes tener un 95 % de cobertura y seguir rompiendo producción.

Lo importante es que los tests aporten confianza.

---

# La pirámide sigue teniendo sentido

Explicaría algo parecido a esto:

```
          E2E
        --------
    Integration
  -----------------
      Unit Tests
```

Y añadiría:

- muchos unitarios
- suficientes de integración
- pocos E2E

No porque sea una moda, sino porque es la forma más barata de detectar errores.

---

# Vitest: rápido porque no intenta parecer Jest

Hablaría de ventajas reales:

- arranque instantáneo
- usa Vite
- TypeScript sin configuraciones raras
- watch muy rápido

No dedicaría mucho tiempo a la configuración.

La configuración debería ocupar menos del 10 % del artículo.

---

# Testing Library cambia la forma de pensar

Aquí está una de las partes más interesantes.

En lugar de esto:

```ts
wrapper.find(".btn-primary");
```

prefiero:

```ts
screen.getByRole("button", {
  name: /guardar/i,
});
```

¿Por qué?

Porque el usuario nunca busca una clase CSS.

Busca un botón.

Eso hace que los tests sobrevivan a los cambios de diseño.

---

# El mayor error que veo

Muchísima gente hace esto:

```ts
expect(wrapper.vm.loading).toBe(true);
```

Eso no prueba nada.

Lo correcto sería comprobar lo que ve el usuario.

```ts
expect(screen.getByRole("progressbar")).toBeVisible();
```

La diferencia parece pequeña.

No lo es.

---

# MSW: el cambio que más impacto ha tenido

Aquí dedicaría bastante espacio.

Antes hacíamos:

```ts
vi.mock(...)
```

para todo.

Ahora prefiero interceptar HTTP.

¿Por qué?

Porque el componente no sabe que está siendo testeado.

Hace exactamente la misma petición que haría en producción.

Solo cambia quién responde.

Eso hace que los tests sean muchísimo más reales.

---

# Los handlers deben contar historias

En vez de:

```ts
return {
  id: 1,
};
```

Prefiero algo así:

```
user-active.ts

user-without-permissions.ts

server-error.ts

empty-result.ts

expired-session.ts
```

Cuando lees un test entiendes inmediatamente el escenario.

---

# Evita mocks gigantes

Si necesitas mockear media aplicación para probar un botón...

...probablemente el problema no es el test.

Es el componente.

Los tests también sirven para detectar componentes demasiado acoplados.

---

# Lo que nunca testeo

Aquí puedes ser algo más contundente.

No testeo:

- propiedades internas
- computed privados
- composables de Vue
- clases CSS
- implementación

Testeo comportamiento.

---

# Una estructura que funciona

```
tests/

components/

composables/

mocks/

handlers/

fixtures/

factories/

utils/
```

Separar fixtures, factories y handlers hace que el proyecto crezca sin convertirse en un caos.

---

# Errores que he cometido

Esta sección aporta mucha credibilidad.

Por ejemplo:

- usar demasiados snapshots
- abusar de `data-testid`
- mockear absolutamente todo
- crear helpers mágicos
- compartir estado entre tests
- depender del orden de ejecución

---

# Conclusión

Podrías cerrar con una idea como esta:

> Un buen test no demuestra que el código funciona. Demuestra que el usuario puede seguir utilizando la aplicación cuando el código cambia. Si una refactorización rompe un test sin cambiar el comportamiento, probablemente el problema esté en el test, no en la refactorización.
