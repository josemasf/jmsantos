## Novedades prioritarias

### 1. P1 · Vitest 5.1: tests afectados sin depender de Git

**Qué cambió — 2/11/2026, estable.** Vitest 5.1 introduce `vitest run --since-last-run` (función **experimental**). La primera ejecución registra los archivos que carga cada test —incluidos imports dinámicos, mocks, setup y snapshots— y las posteriores comparan tiempos de modificación. Los tests que fallaron vuelven a ejecutarse hasta pasar. A diferencia de `--changed`, no depende de un diff Git. También añade revisión individual de snapshots en watch mode (tecla `i`), y **Trace View** en Browser Mode pasa a modo estable `failure-only` por defecto; las trazas incluyen una vista del árbol accesible. Existe además `experimental.traceTimeline` para esperas de tests Node.

**Por qué importa.** En un flujo agéntico, ejecutar la suite completa después de cada edición consume tiempo y recursos; seleccionar tests afectados permite ciclos de feedback más cortos. Las trazas y la vista ARIA ayudan a entender fallos de interacción sin añadir `waitForTimeout` o aumentar reintentos a ciegas.

**Límites.** La selección es experimental y depende del registro de dependencias y del estado local de la ejecución. No sustituye la suite completa de CI, las pruebas E2E ni el análisis de contratos. Las trazas de Browser Mode no se aplican automáticamente a tests jsdom.

**Qué probar.** En una rama de un repositorio que ya use Vitest 5, ejecutar primero la suite completa, modificar un componente y comparar el número de tests seleccionados y el tiempo de `--since-last-run`. Ejecutar después la suite completa y comprobar que no aparecen fallos adicionales. Para Browser Mode, provocar un fallo controlado de rol o nombre accesible y revisar la traza.

**Qué ignorar.** No migrar desde Vitest 4 solo por la función experimental ni hacer depender CI de un historial local efímero.

**Fuente:** [anuncio oficial Vitest 5.1](https://vitest.dev/blog/vitest-5-1).

### 2. P1 · Playwright 1.65: menos ruido en informes y control de tests exclusivos

**Qué cambió — 5/11/2026, estable.** Playwright 1.65 añade el reporter `failures` y `onlyFailures: true` para HTML, JSON y JUnit, que retienen los casos inesperados, flaky e interrumpidos. Añade un lock `-exclusive-` para tests que no deben solaparse con otros. El runner puede ejecutarse bajo Bun con `bunx --bun playwright test`, con limitaciones explícitas.

**Cambios que pueden romper tests.** Los campos de clase TypeScript ahora respetan `useDefineForClassFields`. Los Page Objects que inicializan propiedades usando parameter properties del constructor pueden fallar en runtime. Acciones como `click`, `fill` y `check` esperan ahora que el elemento no sea `inert`: un test que antes interactuaba con un control inactivo puede terminar en timeout. Esto suele revelar una interacción inválida, no necesariamente una regresión de la aplicación.

**Por qué importa.** Los informes centrados en fallos reducen el coste de investigar CI. Los locks exclusivos pueden estabilizar tests que comparten un servidor o un estado global, aunque no sustituyen el aislamiento correcto.

**Qué probar.** Ejecutar una rama con Playwright 1.65; buscar Page Objects con inicializadores de campos que dependan de parámetros del constructor; probar diálogos, overlays y contenido con `inert`; comparar los artefactos de CI antes y después de activar `onlyFailures`.

**Qué ignorar.** No cambiar de Node a Bun por una nueva opción del runner: carece de watch mode y presenta diferencias en compilación, stack traces y trazas.

**Fuente:** [Playwright 1.65 — release oficial](https://github.com/microsoft/playwright/releases/tag/v1.65.0).

### 3. P1 · pnpm 12.18: las skills distribuidas por paquetes requieren aprobación

**Qué cambió — 5/11/2026, estable.** `pnpm approve` puede seleccionar individualmente las skills de una dependencia y en qué directorios de agentes se enlazan. La configuración registra `permissions.<pkg>.skills` y `skills.dirs`. Cambia además la convención de nombres de enlaces: se utiliza el nombre de la skill y, si hay conflicto, uno cualificado por paquete. Se admiten skills anidadas en categorías hasta tres niveles. `pnpm store add` permite preparar instalaciones offline a partir de tarballs; hay correcciones para almacenes compartidos, contenedores y enlaces de ejecutables.

**Por qué importa.** Una skill es contenido de instrucciones para un agente, no simplemente una dependencia pasiva. Vincularla a `.claude/skills` u otro directorio puede cambiar su comportamiento. La aprobación por skill facilita una política de mínimo privilegio, pero requiere revisar el contenido y origen del paquete.

**Qué probar.** En un repositorio de laboratorio, instalar un paquete de prueba que incluya varias skills, revisar qué se ofrece aprobar y qué enlaces se generan. Inspeccionar los cambios en archivos de configuración y `.gitignore`. Si hay builds offline, probar `pnpm store add` y `pnpm install --offline --frozen-lockfile`.

**Qué ignorar.** Las optimizaciones de registries `pnpr` si se utiliza npm o un registry privado convencional: las cifras de benchmarks publicadas no son extrapolables.

**Fuente:** [pnpm 12.18 — release oficial](https://github.com/pnpm/pnpm/releases/tag/v12.18.0).

### 4. P1 condicionado · Hono 4.13.17: endurecimiento posterior al parche de seguridad

**Qué cambió — 7/11/2026, estable.** Tras la 4.13.16 del informe anterior, Hono 4.13.17 ajusta la validación de prefijos `__Secure-` y `__Host-` de cookies sin sensibilidad a mayúsculas/minúsculas, evita coincidencias incorrectas de claves de query string entre separadores y corrige casos de escape de atributos JSX. También añade el nonce CSP a scripts producidos por `ErrorBoundary`, además de otros arreglos de respuesta y tipado.

**Por qué importa.** Los controles de cookies, query strings y escape de HTML son fronteras de seguridad. No todos los proyectos Hono utilizan esas APIs; la prioridad real depende de la exposición.

**Qué probar.** Confirmar con `pnpm why hono`; si está presente, evaluar actualización a 4.13.17 y ejecutar regresiones negativas de autenticación, cookies, validación, rutas y serialización. No asumir que este patch corrige todas las posibles vulnerabilidades del backend.

**Qué ignorar.** No iniciar una migración a Hono 5 RC ni refactorizar el backend por cambios menores.

**Fuente:** [Hono 4.13.17 — release oficial](https://github.com/honojs/hono/releases/tag/v4.13.17).

## Deep dive · Una estrategia de tests para agentes: feedback rápido sin falsa confianza

**Problema.** Un agente puede modificar un componente, ejecutar 20–40 minutos de tests y repetir el ciclo varias veces. Si la suite es lenta o poco fiable, el coste no es solo tiempo: el agente puede interpretar falsos fallos como regresiones y empezar a tocar código no relacionado.

**Propuesta.** Separar dos garantías:

1. **Durante la implementación:** ejecutar tests afectados, tipado del módulo y lint de archivos modificados. El objetivo es acortar feedback, no certificar la PR.
2. **Antes de finalizar:** ejecutar la suite completa requerida, tests de integración relevantes y E2E críticos; publicar resultados reproducibles. El resultado de la fase rápida nunca se comunica como validación total.

Vitest 5.1 permite probar una selección basada en dependencias sin depender del estado de Git. Esto es especialmente útil en worktrees y sesiones que hacen commits intermedios. Sin embargo, si un agente cambia configuración global, contratos o infraestructura, una selección local puede ser insuficiente. Un cambio de MSW, setup o versiones de paquetes exige pruebas amplias.

**Ventajas:** ciclos de feedback cortos, menos ejecuciones redundantes y menor incentivo para desactivar tests lentos. **Desventajas:** mecanismo experimental, estado local, riesgo de dependencias no observadas y falsa confianza si se elimina la pasada completa.

**Decisión recomendada:** piloto con métricas en un repositorio; no convertir `--since-last-run` en la única comprobación de CI. En `AGENTS.md` documentar explícitamente la distinción entre validación incremental y validación final.

## Radar de herramientas y prácticas

**1. Práctica: revisión de snapshots uno a uno en Vitest 5.1.** Problema: un `-u` indiscriminado puede aceptar regresiones visuales o de estructura. **Ventaja:** aceptar o rechazar cada diff, incluyendo snapshots ARIA. **Límite:** sigue requiriendo criterio humano; no demuestra por sí solo corrección funcional. **Madurez:** integrada en release estable. **Alternativas:** revisión de diffs en PR y snapshots de Playwright. **Experimento:** cambiar dos snapshots deliberadamente, aceptar solo uno en watch mode y comprobar el diff final.

**2. Práctica: reporter Playwright solo de fallos.** Problema: informes enormes dificultan localizar fallos reales. **Ventaja:** artefactos más orientados al diagnóstico. **Límite:** pierde contexto de ejecuciones correctas; conservar informes completos periódicos puede ser útil para auditoría. **Madurez:** funcionalidad estable de Playwright 1.65. **Alternativas:** filtros de HTML reporter y herramientas de CI. **Experimento:** ejecutar una suite pequeña con un fallo, un retry y un éxito; comparar los reportes con y sin `onlyFailures`.

No se proponen nuevos servicios externos esta semana: las capacidades anteriores resuelven problemas concretos sin añadir otra plataforma.

## Experimento recomendado (25 minutos)

**Hipótesis:** la selección incremental de Vitest 5.1 reduce ejecuciones durante la implementación sin ocultar fallos en la pasada completa.

1. **5 min:** crear una rama en un proyecto de laboratorio ya compatible con Vitest 5 y ejecutar `pnpm exec vitest run --since-last-run` para registrar la base.
2. **5 min:** modificar una función o componente y ejecutar de nuevo el comando. Registrar tests seleccionados y tiempo.
3. **5 min:** introducir un fallo deliberado en un test relacionado, comprobar que se reejecuta y corregirlo.
4. **5 min:** ejecutar `pnpm exec vitest run` y comparar el resultado con la selección incremental.
5. **5 min:** registrar los datos y decidir si incluir el comando como sugerencia en `AGENTS.md`.

**Éxito:** selección coherente con el cambio, fallos detectados y suite completa final verde. **Fracaso:** cualquier error que solo aparezca en la pasada completa debe investigarse antes de recomendar el flujo.
