## Resumen ejecutivo

1. **P0 — Seguridad de las herramientas de desarrollo.** Cursor confirmó que distribuyó dos builds maliciosas de la extensión Claude Code (2.1.312 y 2.1.313) desde su marketplace el 29/10. No hay evidencia de que la distribución oficial de Anthropic estuviera afectada. Es necesario identificar instalaciones potencialmente expuestas y tratar los positivos como incidentes, no como simples actualizaciones.
2. **P0 — Hono 4.13.16 corrige cinco fallos de seguridad**, incluidos saltos de middleware en rutas montadas o wildcard, omisión de validación de formularios, inyección HTML en el helper CSS y una excepción de CSRF. Revisar inmediatamente **si Hono está en las dependencias**.
3. **P0 — Los navegadores integrados de agentes merecen una política específica.** Una investigación publicada el 29/10 demostró lecturas de archivos locales fuera del ámbito previsto en Codex, VS Code y Claude Desktop. Según los investigadores, Codex y VS Code seguían sin parche el día de publicación. No se ha confirmado en esta revisión un parche posterior.
4. **P1 — Node 26 ya es LTS**, pero no obliga a migrar inmediatamente desde Node 24. pnpm 12.17.0 también corrige problemas reales de instalación en Docker y workspaces.
5. **P1 — Observabilidad y datos remotos:** Sentry JavaScript 11.10.0 añade túnel gestionado y cambia nombres de origen de spans; TanStack Vue Query 5.105.1 y Vue Virtual 3.13.51 corrigen casos concretos de tipos y observadores. Actualizar solo si los casos aplican.

No hay motivos nuevos para iniciar migraciones generales a Vue 3.6 RC, PrimeVue 5, Vitest beta o Astro beta. La prioridad de esta semana es **reducir superficie de ataque y verificar contratos**.

## Novedades prioritarias

### 1. P0 — Extensión Claude Code alterada en el marketplace de Cursor

**Hecho, 29/10/2026.** Cursor publicó un aviso oficial sobre versiones **2.1.312 y 2.1.313** de \x60anthropic.claude-code\x60 distribuidas en su marketplace para macOS y Windows durante una ventana aproximada de once horas. Contenían código ajeno a Anthropic que intentaba añadir una clave SSH no autorizada, establecer persistencia y abrir un túnel. Cursor retiró los paquetes, reconstruyó el marketplace y desactivó el servidor de los atacantes. La empresa indica que el acceso remoto normalmente fallaba por falta de permisos de administrador, **pero eso no descarta modificaciones locales ni exposición**.

**Por qué importa.** El código de una extensión se ejecuta en el entorno del desarrollador, donde pueden residir credenciales de Git, npm, cloud y CI. El nombre del editor o del editor de la extensión no es garantía suficiente de integridad.

**Hacer:** inventariar instalaciones de Cursor y extensiones; buscar ambas versiones y los indicadores publicados. En Windows, revisar también los directorios de extensiones y las claves autorizadas; una instalación limpia de VS Code desde el marketplace oficial no debe confundirse con una instalación afectada. Si hay indicios, **aislar, preservar evidencia, usar la remediación oficial y rotar credenciales desde otro equipo**. Desinstalar sin más no elimina necesariamente la persistencia. Para máquinas no expuestas, no hay motivo para rotaciones masivas.

**Ignorar:** titulares que afirman que *todas* las instalaciones de Claude Code están comprometidas.

**Fuente primaria:** [aviso de Cursor (incluye indicadores y scripts)](https://cursor.com/blog/claude-code-extension-security-notice).

### 2. P0 — Hono 4.13.16: el middleware de seguridad puede no ejecutarse

**Hecho, estable, 01/11/2026.** La versión **4.13.16** corrige cinco casos de seguridad:

- \x60mount()\x60 y \x60app.mount()\x60: determinadas rutas manipuladas podían evitar middleware limitado al prefijo montado.
- \x60RegExpRouter\x60 (también usado por \x60SmartRouter\x60): algunas rutas con comodines o terminadores de línea codificados omitían middleware.
- \x60validator('form')\x60: parámetros adicionales en \x60multipart/form-data\x60 podían evitar la validación prevista.
- Helper \x60css\x60: combinación de segmentos de plantilla capaz de introducir cierre de \x60</style>\x60 e inyección HTML.
- \x60csrf()\x60: las peticiones \x60text/ping\x60 generadas por auditoría de enlaces no recibían la comprobación prevista.

**Por qué importa.** La existencia de un middleware de autenticación, autorización o validación **no garantiza** que todas las variantes de ruta pasen por él. El riesgo es mayor cuando se montan subaplicaciones o se utilizan rutas dinámicas. La versión también endurece el manejo de determinados JWT. Algunos patrones de ruta previamente aceptados ahora lanzan errores; si se usa \x60PreparedRegExpRouter\x60, hay que regenerar sus datos.

**Hacer:** ejecutar \x60pnpm why hono\x60 en repositorios que puedan utilizarlo; si está presente, actualizar a **4.13.16 o superior**, probar rutas montadas, autorización, formularios y CSRF. Añadir tests negativos: peticiones malformadas deben acabar en 400/403/404 y **nunca** llegar al handler protegido. Validar compatibilidad del router antes de desplegar.

**Ignorar:** un refactor del backend entero; el parche es focalizado, aunque requiere tests de regresión.

**Fuente primaria:** [Hono 4.13.16](https://github.com/honojs/hono/releases/tag/v4.13.16).

### 3. P0 — EMBRACE: navegador integrado no equivale a navegador aislado

**Hecho e incertidumbre, 29/10/2026.** Forever Security publicó pruebas sobre navegadores integrados en Cursor, GitHub Copilot, Codex, VS Code y Claude Desktop. Son **fallos diferentes**, no una CVE común. Para Codex, VS Code y Claude Desktop describen acceso a archivos locales fuera de la carpeta esperada tras abrir una página HTML local en el navegador integrado; en VS Code y Claude Desktop la demostración implicaba web workers. El informe atribuye a Cursor una vía de ejecución mediada por instrucciones al agente y a Copilot suplantación de dirección. Los investigadores indican que Cursor y Copilot habían corregido sus casos y que **Codex y VS Code seguían sin corrección al publicar**. El estado de la variante de Claude Desktop y las versiones concretas afectadas no están completamente delimitados.

**Por qué importa.** El riesgo aparece cuando un proyecto o página no fiable se abre dentro de una superficie con permisos adicionales; no es equivalente a simplemente abrir VS Code o usar el CLI de Codex. El ataque descrito contra archivos locales requería que se abriese un HTML mediante un enlace.

**Hacer:** no abrir HTML local de repositorios desconocidos en navegadores integrados; tratar los enlaces generados por agentes como contenido no confiable; usar entornos aislados sin secretos para investigar proyectos externos; actualizar las aplicaciones y seguir avisos oficiales. Documentar una política de Workspace Trust, extensiones y navegación de agentes.

**Ignorar:** concluir que todos los agentes ejecutan código malicioso al abrir un repositorio. La investigación no demuestra eso.

**Fuentes:** [investigación original de Forever Security](https://forever.security/blog/embrace-hacking-5-ai-assistants-embedded-browsers/) y [cobertura técnica con contexto de divulgación](https://www.theregister.com/security/2026/10/29/researchers-find-bugs-in-5-ai-developer-tools-with-openai-and-microsoft-flaws-still-unpatched/5306508).

### 4. P1 — Node 26.13.0 entra en LTS: planificar, no precipitarse

**Hecho, estable, 28/10/2026.** Node **26.13.0 “Lithium”** marca la transición de la rama 26 a LTS, con soporte anunciado hasta abril de 2029. Node **24.22.2** se publicó el mismo día y sigue soportado. El cambio de 26.12.1 a 26.13.0 se centra en metadatos de la fase LTS, no en una nueva gran API.

**Por qué importa.** Node es la base de Vite, Vitest, pnpm, scripts de CI, Dev Containers y algunos backends. Migrar puede afectar módulos nativos, imágenes Linux y herramientas con restricciones \x60engines\x60. Desde Node 25, los binarios oficiales Linux pueden requerir \x60libatomic\x60.

**Hacer:** mantener Node 24 parcheado en producción y añadir **Node 26** como job no bloqueante de compatibilidad. Probar instalación limpia, build, tests, módulos nativos y contenedores. Convertir el job en bloqueante cuando dependencias y tiempos de CI lo permitan.

**Ignorar:** convertir el anuncio LTS en una migración urgente de todos los repositorios.

**Fuentes:** [Node 26.13.0](https://github.com/nodejs/node/releases/tag/v26.13.0) y [Node 24.22.2](https://github.com/nodejs/node/releases/tag/v24.22.2).

### 5. P1 — pnpm 12.17.0 corrige reproducibilidad real en Docker y monorepos

**Hecho, estable, 30/10/2026.** pnpm **12.17.0** introduce selectores por grupo y comodines en \x60overrides\x60, amplía la actualización de versiones de runtimes y corrige varios problemas de instalación. Destacan permisos de archivos generados que impedían a otro usuario ejecutar comandos en imágenes Docker, enlaces rotos con \x60node_modules\x60 enlazado y detección incompleta de cambios en dependencias locales. También corrige escenarios de \x60--frozen-lockfile\x60 y del store virtual global. La rama 11 recibió correcciones de mantenimiento en **11.28.10**.

**Por qué importa.** Son fallos que pueden manifestarse como CI no reproducible, diferencias entre desarrollo y producción o instalaciones que dicen estar actualizadas sin estarlo. La mejora de permisos importa especialmente para contenedores que construyen como root y ejecutan con un usuario sin privilegios.

**Hacer:** en repositorios que ya estén en pnpm 12, evaluar 12.17.0 en una PR pequeña; comprobar instalación limpia y repetida, \x60--frozen-lockfile\x60, ejecución con usuario no root y cambios en paquetes \x60workspace:\x60. En pnpm 11, actualizar dentro de su rama si procede.

**Ignorar:** adoptar comodines de overrides sin un conflicto de dependencias concreto.

**Fuente:** [pnpm 12.17.0](https://github.com/pnpm/pnpm/releases/tag/v12.17.0).

### 6. P1 — Sentry JavaScript 11.10.0: túnel de eventos y nombres de spans

**Hecho, estable, 28/10/2026.** El SDK **11.10.0** añade un túnel gestionado: el cliente puede usar \x60tunnel: true\x60 y un servidor compatible instalar \x60serveTunnelIntegration()\x60. Esto permite encaminar eventos por un servidor propio cuando bloqueadores impiden el envío directo. El soporte automático se documenta para frameworks como Astro, Nuxt y Nitro, no para una SPA Vue estática sin backend. Además, cambian varios valores de *span origin* para alinearse con las convenciones de tracing, incluidos orígenes de métricas web que pasan de \x60auto.http.browser.*\x60 a \x60auto.ui.browser.*\x60.

**Por qué importa.** Un túnel puede mejorar la recepción de telemetría, pero consume infraestructura propia y exige proteger el endpoint frente a abuso. Los cambios de nombres pueden afectar reglas \x60ignoreSpans\x60, consultas y alertas, aunque el SDK se actualice sin errores.

**Hacer:** comprobar primero la major instalada. Si se utiliza Sentry 11 y hay eventos bloqueados, probar el túnel en un entorno con servidor compatible; medir entrega, carga y costes. Revisar filtros y dashboards basados en los orígenes anteriores.

**Ignorar:** montar un proxy nuevo si la telemetría actual funciona bien o actualizar de major solo por el túnel.

**Fuente:** [Sentry JavaScript 11.10.0](https://github.com/getsentry/sentry-javascript/releases/tag/11.10.0).

### 7. P1 condicionado — TanStack Vue Query y Vue Virtual: correcciones específicas

**Hecho, estable, 01/11/2026.** \x60@tanstack/vue-query@5.105.1\x60 corrige la selección de sobrecargas TypeScript de \x60infiniteQueryOptions\x60 cuando \x60initialData\x60 puede ser indefinido. También elimina \x60fetchStatus\x60 de los filtros de \x60isFetching\x60/\x60useIsFetching\x60, ya que estas APIs cuentan exclusivamente consultas en estado fetching. \x60@tanstack/vue-virtual@3.13.51\x60 deja de observar scroll cuando el elemento se vuelve nulo; el core corrige un caso donde una lista reducida dejaba de cubrir el viewport.

**Por qué importa.** La primera corrección puede desbloquear typechecks de infinite queries. La segunda evita observadores obsoletos y anomalías visuales en tablas o listados virtualizados tras filtros y cambios de tamaño.

**Hacer:** actualizar si se usan estas librerías y reproducir el escenario afectado. En Virtual, probar filtros que reduzcan una lista larga mientras el usuario está desplazado cerca del final.

**Ignorar:** adoptar TanStack Query o Virtual solo porque haya una patch release. Su adopción requiere una decisión de arquitectura independiente.

**Fuentes:** [Vue Query 5.105.1](https://github.com/TanStack/query/releases/tag/%40tanstack/vue-query%405.105.1) y [Vue Virtual 3.13.51](https://github.com/TanStack/virtual/releases/tag/%40tanstack/vue-virtual%403.13.51).

## Deep dive — ¿Qué debe poder hacer un agente en el equipo de desarrollo?

Los incidentes de esta semana comparten un problema de **límites de confianza**. No son equivalentes: uno es un compromiso de distribución de una extensión, otro es una superficie de navegador con permisos inesperados. Pero ambos invalidan la suposición de que “si está dentro del editor, es seguro”.

**Modelo propuesto:**

1. **Código y documentos externos:** tratar README, HTML, logs, respuestas MCP y tickets como datos, no como instrucciones privilegiadas.
2. **Ejecución:** separar lectura/análisis de comandos con efectos. Para cambios autónomos, usar worktree y runner efímero o contenedor aislado.
3. **Secretos:** no montar credenciales de producción en entornos de agentes; proporcionar credenciales de alcance mínimo y revocables.
4. **Red:** restringir destinos cuando sea viable y registrar accesos sensibles.
5. **Validación:** tests y CI fiables antes de PR; revisión humana para permisos, contratos y despliegue.
6. **Trazabilidad:** conservar commit, ticket, versión del agente, checks ejecutados y resultado de revisión.

**Ventaja:** reduce el impacto de contenido hostil y facilita reproducir resultados. **Coste:** preparar runners, datos de prueba y políticas requiere trabajo inicial; una sandbox mal configurada puede bloquear tareas legítimas o dar falsa seguridad.

**Decisión recomendada:** empezar con un flujo de agente para un único repositorio, en un entorno desechable con datos ficticios y sin secretos. No dar acceso a todos los repositorios ni activar modos de omisión de permisos como solución al exceso de confirmaciones.

## Radar de herramientas y prácticas — dos candidatas

### A. oasdiff — detectar cambios incompatibles de OpenAPI

**Problema:** un backend modifica el contrato y el frontend descubre la incompatibilidad demasiado tarde. **Solución:** \x60oasdiff breaking\x60 compara dos especificaciones OpenAPI y clasifica cambios potencialmente incompatibles; puede ejecutarse localmente o en CI. **Ventaja:** feedback antes de integrar, independiente de .NET, Hono o Vue. **Límite:** detecta cambios en la especificación, no discrepancias entre especificación e implementación. Requiere OpenAPI actualizada. **Madurez:** herramienta OSS con CLI y acción de GitHub; existe oferta comercial opcional para aprobación de cambios. **Alternativas:** OpenAPI Diff, pruebas de contrato consumidor-proveedor (por ejemplo, Pact).

**Experimento:** comparar la OpenAPI de \x60master\x60 con una rama que añada una propiedad obligatoria a un request; exigir un resultado de incompatibilidad antes del merge. [Documentación oficial](https://www.oasdiff.com/docs/getting-started).

### B. Testcontainers para .NET + SQL Server — datos de integración reproducibles

**Problema:** QA compartido no dispone siempre del estado necesario para probar un flujo. **Solución:** levantar SQL Server aislado por suite de integración, aplicar migraciones y scripts semilla y destruirlo después. **Ventaja:** casos repetibles y sin colisiones entre desarrolladores; compatible con el ecosistema de pruebas .NET. **Límites:** requiere Docker compatible, memoria, tiempo de arranque y aceptación de licencia de la imagen; no sustituye automáticamente un entorno E2E completo ni resuelve aplicaciones legacy incompatibles con contenedores. **Madurez:** proyecto establecido con módulo oficial para SQL Server. **Alternativas:** docker-compose con snapshots/semillas y bases efímeras administradas.

**Experimento:** levantar un contenedor MSSQL, aplicar un script de escenario y verificar una consulta de integración dos veces con idéntico resultado. [Módulo oficial](https://dotnet.testcontainers.org/modules/mssql/).

## Experimento recomendado (20–30 minutos)

**Objetivo:** demostrar que un contrato incompatible no llega inadvertido al frontend.

1. Tomar dos versiones no sensibles de un OpenAPI válido (5 min).
2. Cambiar en la segunda un campo opcional del request a obligatorio (5 min).
3. Ejecutar \x60oasdiff breaking --fail-on ERR base.yaml revision.yaml\x60 (5 min).
4. Comprobar el código de salida y el diagnóstico; revertir el cambio y repetir (5 min).
5. Documentar cómo añadir la comprobación al pipeline y quién aprobaría una excepción (5 min).

**Resultado esperado:** falla ante el cambio incompatible y pasa cuando no existe. **Éxito:** la detección es reproducible, explica el endpoint afectado y puede incorporarse a CI sin publicar contratos privados en servicios externos.
