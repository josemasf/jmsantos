## Resumen ejecutivo

Esta semana destacan cinco temas:

1. **Node 24.22.1:** actualización de seguridad publicada el 21 de octubre. Prioridad operativa.
2. **TypeScript 7.1 Beta:** nuevas interfaces de integración para herramientas y frameworks, especialmente *Content Mappers* para archivos como `.vue`.
3. **Vuetify 4.3 estable:** mejoras en tablas, componentes, Material Design 3 y accesibilidad.
4. **pnpm 12.15:** configuración reutilizable entre repositorios y endurecimiento de la resolución desde registries.
5. **Agentes de IA:** métricas más detalladas de adopción en GitHub Copilot y un enfoque de memoria histórica fechado y asociado a commits en `mattpocock/skills`.

El resto del stack requiere principalmente mantenimiento y validación, no rediseños.

## 1. TypeScript 7.1 Beta: integración más sólida con Vue

**Qué cambió.** La beta de TypeScript 7.1 incorpora APIs de extensibilidad para frameworks. Los *Content Mappers* permiten asociar contenido original, como un SFC `.vue`, con una representación TypeScript que pueda analizar el compilador nativo. También se presentaron puntos de entrada síncronos, asíncronos, de AST y de sistemas de archivos virtuales.

**Por qué importa.** Vue Language Tools y `vue-tsc` necesitan mapear diagnósticos, autocompletado y navegación entre los bloques de un componente y sus representaciones virtuales. Una API oficial puede reducir complejidad y permitir aprovechar mejor la velocidad del compilador nativo. **No significa que `tsc` sustituya hoy a `vue-tsc`**: la compatibilidad depende de las herramientas del ecosistema.

**Qué probar.**
- Crear un paquete TypeScript puro separado y evaluar `typescript@beta`.
- Comparar tiempo, memoria y diagnósticos con la versión actual.
- Seguir la integración de Vue Language Tools con Content Mappers.
- Conservar una matriz que cubra editor, `vue-tsc`, Vite y Vitest antes de cambiar el baseline Vue.

**Qué ignorar.** No incorporar las nuevas APIs en aplicaciones de negocio ni forzar TypeScript 7.1 Beta en un proyecto Vue productivo.

**Referencia:** [TypeScript Blog](https://devblogs.microsoft.com/typescript/).

## 2. Node 24.22.1: seguridad antes que nuevas funcionalidades

**Qué cambió.** El briefing recoge las actualizaciones de seguridad del 21 de octubre: Node 22.23.4, 24.22.1 y 26.12.1. Se describen problemas de severidad alta, entre ellos uno en Brotli para cargas comprimidas manipuladas, además de correcciones relacionadas con TLS, DNS y conexiones HTTP.

**Por qué importa.** Node ejecuta builds, tests, herramientas, CI y, en algunos productos, SSR y backend. La exposición real depende de qué funciones se usan y de si el proceso trata entradas no confiables.

**Qué probar.**
```bash
node --version
pnpm install --frozen-lockfile
pnpm exec vitest run
pnpm exec vue-tsc --noEmit
pnpm build
```
Actualizar imágenes Docker, Dev Containers y runners cuando corresponda.

**Qué ignorar.** No migrar automáticamente a Node 26 solo por una actualización de seguridad: aplicar el parche de la rama LTS utilizada.

**Referencia:** [Node.js — Security Releases](https://nodejs.org/en/blog/vulnerability).

## 3. Vuetify 4.3 estable: componente, sistema visual y accesibilidad

**Qué cambió.** Vuetify 4.3.0, presentado como *Paladin*, se publicó el 19 de octubre. `VAvatarGroup`, `VHighlight` y `VProgress` pasan desde Labs a la librería principal. `VDataTable` añade la estrategia de selección `filtered` y datos adicionales sobre selección y expansión. También evoluciona Material Design 3 y mejora la accesibilidad de controles como sliders.

**Por qué importa.** Es una oportunidad para reducir código ad hoc en tablas de negocio y centralizar tokens, defaults y estilos. Las nuevas APIs no justifican por sí solas migrar una app Vuetify 3.

**Qué probar.**
- Una vertical de `VDataTable` con filtros, selección múltiple y expansión.
- Formularios con teclado y lector de pantalla; verificar el estado y foco accesibles.
- Un Storybook comparativo y pruebas visuales para botones, tabs y alertas.
- Medir wrappers y CSS local que se pueden eliminar, no solo componentes migrados.

**Qué ignorar.** Nuevas APIs de Labs sin un caso concreto; no conservar wrappers innecesarios por inercia.

**Referencia:** [Vuetify releases](https://github.com/vuetifyjs/vuetify/releases).

## 4. pnpm 12.15: configuración compartida y supply chain

**Qué cambió.** El briefing destaca configuración reutilizable mediante `include` en `pnpm-workspace.yaml`, políticas de arranque para la configuración compartida, validación del nombre real de paquetes devueltos por registries (`ERR_PNPM_REGISTRY_NAME_MISMATCH`) y opciones de reproducibilidad del lockfile como `integrityTarget`.

**Por qué importa.** Las políticas de instalación, confianza y registries suelen divergir cuando se copian manualmente entre repositorios. Pero una configuración central también necesita una cadena de confianza sólida.

**Qué probar.**
- Crear un piloto que herede configuración común.
- Inspeccionar el origen de paquetes cuando se usan registries privados.
- Confirmar que la instalación es reproducible:
```bash
pnpm install --frozen-lockfile
pnpm build
pnpm exec vitest run
```
- Revisar cambios en `pnpm-lock.yaml` y compatibilidad con CI.

**Qué ignorar.** Nuevos ajustes de integridad y tarballs sin necesidad operativa ni validación del registry.

**Referencia:** [pnpm releases](https://github.com/pnpm/pnpm/releases).

## 5. GitHub Copilot: adopción de agentes, skills y MCP

**Qué cambió.** El briefing recoge métricas más detalladas sobre skills, agentes, comandos, plugins y uso por cliente, útiles para comprender adopción y consumo en la organización.

**Por qué importa.** Permite formular preguntas sobre qué herramientas usa el equipo, pero el número de solicitudes o tokens **no es una métrica de productividad**.

**Qué probar.** Construir un informe mensual agregado sobre adopción de skills y MCP, contrastado con tiempo hasta PR aceptable, cambios solicitados en review, defectos y fiabilidad de CI.

**Qué ignorar.** Rankings personales basados en prompts o tokens consumidos.

**Referencia:** [GitHub Copilot changelog](https://github.blog/changelog/label/copilot/).

## 6. Matt Pocock Skills: memoria con fecha, evidencia y commit

**Qué cambió.** El briefing señala un cambio del 19 de octubre en la skill experimental `chief-of-staff`: una wiki Markdown persistente con operaciones de incorporación, consulta y revisión de conocimientos, vinculando afirmaciones al momento y commit en que eran verdaderas.

**Por qué importa.** Un agente de larga duración puede basarse en supuestos obsoletos. Registrar decisiones con contexto temporal ayuda a entender cómo evolucionó la arquitectura, sin reescribir silenciosamente la historia.

**Qué probar.**
```text
wiki/
  index.md
  architecture/
  decisions/
  problems/
```
- Mantener `AGENTS.md` breve y operativo.
- Documentar ADRs o decisiones duraderas con fecha, evidencia y commit.
- Marcar explícitamente las decisiones sustituidas.
- Comprobar que una consulta recupera el estado vigente y no solo una decisión antigua.

**Qué ignorar.** Generar automáticamente una wiki inmensa sin dueño ni mantenimiento.

**Referencia:** [mattpocock/skills](https://github.com/mattpocock/skills).

## 7. Vue 3.6 RC13: reactividad y compatibilidad antes que Vapor

**Qué cambió.** Según el briefing, Vue 3.6 RC13 apareció el 23 de octubre y corrige casos de Vapor, transiciones, hidratación, componentes asíncronos, slots y `KeepAlive`. La rama 3.6 incorpora también una implementación renovada de reactividad.

**Por qué importa.** **Actualizar Vue 3.6** y **adoptar Vapor** son dos decisiones distintas. La reactividad afecta también a aplicaciones que siguen con VDOM.

**Qué probar.**
```bash
pnpm up vue@3.6.0-rc.13
pnpm exec vitest run
pnpm exec vue-tsc --noEmit
pnpm build
pnpm exec playwright test
```
Solo en una rama experimental; centrarse en watchers, formularios, `KeepAlive`, `Teleport`, transiciones y librerías UI instaladas.

**Qué ignorar.** Una migración masiva a Vapor antes de estabilidad y compatibilidad.

**Referencia:** [Vue core releases](https://github.com/vuejs/core/releases).

## 8. Quasar 2.35.2: tres correcciones concretas

**Qué cambió.** El briefing recoge correcciones de posicionamiento para `QMenu` y `QTooltip` dentro de Shadow DOM, restauración del scroll en iOS tras cerrar overlays y tratamiento de máscaras de día del año en `extractDate()`.

**Por qué importa.** Impacta componentes de overlay, aplicaciones móviles y utilidades de fecha; no introduce un nuevo modelo arquitectónico.

**Qué probar.** Validar el posicionamiento en web components, navegación iOS con diálogos y round-trip de máscaras de fecha si esas capacidades se usan.

**Qué ignorar.** Refactorización general de componentes si no se está afectado.

**Referencia:** [Quasar releases](https://github.com/quasarframework/quasar/releases).

## 9. Vite 8.3.5: mantenimiento del build

**Qué cambió.** Correcciones sobre precarga e imports de chunks, HMR, sourcemaps, `server.origin` y Bundled Dev Mode.

**Por qué importa.** Los problemas de rutas de assets y precarga a veces se manifiestan solo en producción o en despliegues bajo subrutas.

**Qué probar.**
```bash
pnpm up -D vite@8.3.5
pnpm build
pnpm exec vitest run
```
Añadir una comprobación visual en preview si la aplicación utiliza bases de URL especiales.

**Qué ignorar.** Bundled Dev Mode experimental cuando el tiempo de arranque del dev server no sea un problema real.

**Referencia:** [Vite releases](https://github.com/vitejs/vite/releases).

## 10. Vitest, Testing Library y MSW: consolidar antes que reescribir

**Qué cambió.** El briefing no identifica un cambio estratégico nuevo en esa semana: Vitest 5.0.5, MSW 3.0.3 y Testing Library mantienen las recomendaciones de integración ya analizadas.

**Por qué importa.** La calidad de una suite depende de sus fronteras y del comportamiento observable, no del número de mocks o tests.

```text
Vitest          → runner, aislamiento y ejecución
Testing Library → comportamiento visible
user-event      → interacción
MSW             → frontera HTTP
Playwright      → flujos E2E reales
```

**Qué probar.**
- Verificar reset de handlers entre tests.
- Comprobar casos con fake timers y retrasos simulados.
- Detectar tests redundantes y aserciones sobre detalles internos.
- Mantener migraciones Vitest y MSW en cambios separados.

**Qué ignorar.** Mover todos los tests a Browser Mode o sustituir MSW por mocks internos indiscriminadamente.

**Referencias:** [Vitest](https://vitest.dev/) · [Testing Library](https://testing-library.com/docs/vue-testing-library/intro/) · [MSW](https://mswjs.io/).

## 11. PrimeVue: decisión técnica y de licencia

**Qué cambió.** No se identificó una release nueva significativa durante la semana. PrimeVue 4 conserva la licencia MIT histórica; la evolución del nuevo ecosistema PrimeUI/PrimeVue 5 incluye consideraciones de licencia distintas.

**Por qué importa.** Migrar de 4 a 5 requiere evaluar valor funcional, compatibilidad, coste y condiciones de uso, no solo semver.

**Qué probar.** Si hay necesidad concreta de v5, comparar `DataTable`, formularios, diálogos, navegación, theming, accesibilidad y regresiones visuales antes de decidir.

**Qué ignorar.** Migrar únicamente por no estar en la última major.

**Referencia:** [PrimeVue](https://primevue.org/).

## Plan de acción

1. **Seguridad:** aplicar Node 24.22.1 donde corresponda.
2. **Toolchain:** actualizar Vite 8.3.5 y evaluar pnpm 12.15 por separado.
3. **UI:** pilotar Vuetify 4.3 en una vertical real; parchear Quasar cuando aplique.
4. **Ecosistema Vue:** mantener Vue estable mientras se prueba 3.6 RC13 aisladamente.
5. **Agentes:** probar documentación histórica con referencias a commits y seguir `mattpocock/skills`.
6. **Testing:** consolidar Vitest/Testing Library/MSW sin duplicar fronteras.
7. **Ignore list:** no migrar a Vapor, PrimeVue 5 ni TypeScript 7.1 Beta en producción por inercia.

## Conclusión

La novedad más estratégica es **TypeScript 7.1 y su extensibilidad para frameworks**; la tarea más urgente es **parchear Node**. Vuetify 4.3 y pnpm 12.15 ofrecen mejoras prácticas, pero deberían entrar mediante pilotos controlados.

La dirección de ingeniería sigue siendo la misma: **repositorios reproducibles, reglas explícitas, tests con fronteras justificadas y agentes que trabajan con conocimiento verificable**.
