## Novedades prioritarias

### 1. P1 · Vitest 5.1.1: la fiabilidad de los tests es una propiedad del runner y del test

**Qué cambió — 17/11/2026, estable.** Vitest 5.1.1 corrige fugas de contexto de `expect`, errores de teardown de fixtures duplicados, ordenamiento antes del shuffle con semilla, estado de `expect.assertions` entre reintentos, asignación de un nuevo `AbortSignal` por intento, sharding aplicado antes del arranque y varios casos de cobertura V8. También mejora mensajes de diff y la caché de módulos de filesystem.

**Por qué importa.** Un test que depende del orden de ejecución o deja fixtures abiertos contamina otras pruebas. En CI con sharding y agentes que ejecutan subconjuntos de tests, la variabilidad es especialmente costosa: se atribuyen al código errores que pertenecen al runner o a los propios tests.

**Impacto.** Testing, diagnóstico, fiabilidad de CI y tiempo de revisión. No hay un benchmark publicado aquí que permita prometer una reducción porcentual del tiempo.

**Qué probar.** En una rama con Vitest 5.1, actualizar a 5.1.1 y ejecutar: suite completa, ejecución aleatoria con semilla fija, reintentos de un test controlado y un shard de la matriz real. Inspeccionar que los errores de teardown no se duplican y que los reintentos no heredan estado. Si se usa cobertura V8, comparar el informe de ficheros no ejecutados.

**Qué ignorar.** No migrar una aplicación desde Vitest 4 únicamente por este patch; tampoco dar por resueltos tests flaky que dependen de temporizadores o estado global. **Fuente:** [Vitest 5.1.1](https://github.com/vitest-dev/vitest/releases/tag/v5.1.1).

### 2. P2 · Vite 8.4 beta: seguridad del dev server y configuración futura

**Qué cambió — 16/11/2026, beta.** La beta de Vite 8.4 introduce `server.fs.strict: 'extended'`, capacidades para registrar módulos seguros por entorno, chunks de workers en el manifiesto de build y soporte de bundled dev para SSR. Estabiliza `--configLoader` y depreca `--configLoader=runner`; mueve `css.devSourcemap` hacia `dev.sourcemap.css`. También incluye cambios en preload CSS y eliminación de opciones antiguas del optimizador.

**Por qué importa.** Los servidores de desarrollo remotos, workspaces de agentes y entornos de previsualización tienen límites de acceso a archivos. La gestión de módulos seguros y de configuración puede afectar a plugins internos, SSR y herramientas que modifican la pipeline.

**Impacto.** Arquitectura de tooling y seguridad de desarrollo; posibles incompatibilidades de configuración en una migración futura. No se ha identificado un motivo para actualizar hoy a una beta.

**Qué probar.** Inventariar configuraciones `server.fs`, `css.devSourcemap`, `--configLoader` y optimización de dependencias. Probar en un sandbox si existe un plugin Vite propio o SSR; ejecutar build, tests y preview bajo la ruta base real.

**Qué ignorar.** Bundled Dev SSR y workers en manifest si no se usan. **Fuente:** [Vite 8.4.0-beta.1](https://github.com/vitejs/vite/releases/tag/v8.4.0-beta.1). La última release estable de la serie 8.3 visible en la revisión es 8.3.8 (11/11): no confundir con la beta.

### 3. P1 condicionado · Hono 4.13.20: integridad de la frontera HTTP

**Qué cambió — 22/11/2026, estable.** Hono 4.13.20 ajusta el tratamiento de valores de cookies (rechaza una comilla doble aislada), cabeceras de respuestas HEAD comprimidas, tipos de WebSocket para entornos sin DOM, opciones de cliente y propiedades opcionales al transformar JSON. Incluye arreglos de JSX y adaptadores AWS Lambda.

**Por qué importa.** Los clientes generados o tipados y los handlers de backend comparten contratos de HTTP y serialización. Un cambio pequeño en cookies o respuestas HEAD puede ser visible en proxies, middleware o tests de integración. No se trata de una nueva vulnerabilidad crítica demostrada para todos los proyectos.

**Qué probar.** Comprobar primero `pnpm why hono`. Si se usa, evaluar el patch en una PR aislada, probar autenticación y cookies, respuestas HEAD y los contratos OpenAPI implicados. Si se despliega en AWS Lambda, revisar también los paquetes de adaptador publicados el 22/11.

**Qué ignorar.** Refactorizar rutas o migrar a Hono 5 por esta actualización. **Fuente:** [Hono 4.13.20](https://github.com/honojs/hono/releases/tag/v4.13.20).

### 4. P1 · Matt Pocock Skills: una skill puede existir y no ser instalable

**Qué cambió — commits posteriores al briefing anterior.** El frontmatter de `software-factory` contenía una descripción YAML con dos puntos sin comillas. Un parser estricto interpretaba mal la cabecera y `npx skills add` omitía la skill. Se corrigió el texto entrecomillándolo. Después se añadió un workflow de CI que recorre todos los `SKILL.md`, analiza el frontmatter con el mismo parser YAML utilizado por el instalador y exige `name` y `description` válidos.

**Por qué importa.** Un archivo de instrucciones que no se instala correctamente produce una falsa sensación de automatización. La validez de Markdown no garantiza la validez de metadatos. La integración con Claude Code, Codex o Copilot depende tanto del formato y la instalación como de las herramientas que cada agente admite.

**Qué probar.** En un repositorio de laboratorio, validar las cabeceras con un parser YAML estricto y comprobar instalación y descubrimiento real de cada skill. Incorporar un check similar a CI antes de distribuir skills internas. En `software-factory`, actualizar desde la rama que contiene la corrección si esa skill estaba fallando al instalarse; no actualizar todas las skills por inercia.

**Qué ignorar.** No asumir compatibilidad de ejecución entre asistentes porque todos lean `SKILL.md`: subagentes, permisos, herramientas y eventos no son equivalentes. **Fuentes:** [corrección](https://github.com/mattpocock/skills/commit/9201b96da4af2d663faa13bef984095bb69059b1) · [validación CI](https://github.com/mattpocock/skills/commit/37209058e45b7c60b36218b7392df0ebcceb247a).

## Deep dive · Las skills son dependencias ejecutables del proceso de ingeniería

El error YAML de `software-factory` demuestra una distinción importante: un archivo que parece correcto para una persona puede no ser consumible por un instalador. En una aplicación Vue, el equivalente sería publicar un paquete con `package.json` inválido: el código puede estar bien, pero el consumidor no puede usarlo.

La calidad de una skill tiene al menos cuatro capas:

1. **Integridad del artefacto:** `SKILL.md` presente, frontmatter válido, referencias existentes.
2. **Descubrimiento:** el agente o instalador la encuentra bajo el nombre previsto.
3. **Compatibilidad operativa:** comandos, permisos y subagentes existen en el harness destino.
4. **Eficacia:** la skill produce una mejora observable sobre un conjunto de tareas representativas.

Un check YAML cubre la primera capa, no las otras tres. La segunda exige instalar y listar las skills. La tercera exige una prueba por harness: Claude Code, Codex y Copilot. La cuarta requiere comparar resultados sobre issues reales o fixtures reproducibles, con criterios de aceptación.

**Ventajas de tratar las skills como paquetes:** se detectan errores antes de distribuirlos; es más fácil fijar versiones, revisar cambios y reproducir el comportamiento de un agente. **Costes:** mantener CI, fixtures y una matriz mínima de compatibilidad. **Riesgo:** confundir el éxito de un check de sintaxis con la calidad de la ingeniería generada.

**Decisión recomendada:** añadir validación de frontmatter y un smoke test de instalación a los repositorios que distribuyan skills. Para skills críticas, mantener además un escenario de aceptación por harness. No desplegar cambios de instrucciones externas sin revisar el diff.

## Radar de herramientas y prácticas

**1. Contract tests de instalación de skills (práctica).** Problema: instrucciones que no se cargan o se cargan bajo nombres inesperados. Ventajas: bajo coste, determinismo y feedback temprano. Límites: no valida razonamiento ni permisos. Madurez: técnica convencional de CI aplicada a artefactos agénticos. Alternativa: revisión manual, menos fiable. **Experimento:** romper intencionadamente una descripción YAML y comprobar que la CI falla antes de instalar.

**2. Matriz de fiabilidad de tests con shuffle y reintentos (práctica).** Problema: suites con estado compartido que parecen correctas en un orden fijo. Ventajas: descubre acoplamientos y ayuda a priorizar aislamiento. Límites: una ejecución verde no demuestra ausencia de flakiness; los reintentos pueden ocultar errores. Madurez: técnicas establecidas del testing. Alternativa: ejecutar solo suite completa secuencial, que ofrece menos señales sobre independencia. **Experimento:** ejecutar un subconjunto con varias semillas, registrar fallos y reproducirlos con semilla fija.

No se añaden herramientas SaaS sin evidencia de una necesidad no cubierta.

## Experimento recomendado (25 minutos)

**Objetivo:** validar que las skills del repositorio se pueden descubrir e instalar, no solo que el Markdown se lee.

- **0–5 min:** seleccionar dos skills, una estable y otra experimental, en un repositorio de prueba sin secretos.
- **5–10 min:** analizar frontmatter con YAML estricto, verificando `name` y `description`.
- **10–18 min:** instalar mediante el procedimiento documentado y comprobar los archivos resultantes.
- **18–25 min:** introducir una descripción inválida en una copia y verificar que el check falla. Restaurar y repetir.

**Resultado esperado:** check reproducible en CI y evidencia de instalación. **Éxito:** el caso válido pasa y el caso inválido falla de forma explícita; ningún archivo del proyecto productivo cambia.
