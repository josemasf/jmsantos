## Novedades prioritarias

### 1. P1 · pnpm 12.19–12.21: dependencias repetibles y despliegues más previsibles

**Qué cambió.** pnpm 12.19 (10/11) introduce, entre otras cosas, `pnpm fund`, una mejora del *loaded node linker* para dependencias que requieren build y `projectScopedOptionalPeers`; ofrece además `lockfile.format: v13` como **experimental**. La versión 12.21 (13/11) corrige numerosos problemas con resolución y retención de versiones de peers, `nodeLinker: hoisted`, `pnpm deploy`, lockfiles v13 y almacenamiento offline de dependencias Git y tarballs.

**Por qué importa.** En un monorepo con varias aplicaciones Vue y librerías de componentes, una dependencia peer elegida de forma distinta puede crear instalaciones que funcionan localmente y fallan en CI. Una instalación repetida no debería cambiar los proveedores de peers sin que haya cambiado la intención del desarrollador. La preparación offline de dependencias también resulta útil para builds aislados y entornos reproducibles.

**Impacto.** Positivo para DX, CI y despliegues. No se ha demostrado aquí una mejora de rendimiento concreta. La versión de lockfile v13 es experimental: no cambiar el formato en todos los repositorios.

**Qué probar.** En un worktree, ejecutar dos instalaciones consecutivas y comparar el lockfile y el árbol de dependencias; después ejecutar `pnpm install --frozen-lockfile`, build y tests. Si se utiliza `pnpm deploy`, probar un artefacto desplegable real. Revisar especialmente peers de Vue, Vite, Vitest y librerías UI.

**Qué ignorar.** `pnpm fund`, pnpr remoto y el formato v13 salvo necesidad concreta. **Fuente:** [pnpm 12.21](https://github.com/pnpm/pnpm/releases/tag/v12.21.0) · [pnpm 12.19](https://github.com/pnpm/pnpm/releases/tag/v12.19.0).

### 2. P0 condicionado · pnpm 11.28.12: registries y cadena de suministro

**Qué cambió — 13/11, estable.** En pnpm 11.28.12, una URL de registry que contenga `${VAR}` en configuraciones donde pnpm no expande variables ahora falla explícitamente. Antes podía ignorarse esa URL y resolver paquetes desde otro registry, como npmjs.org. La versión también deja de incluir una versión de undici 6 señalada por escáneres dentro de `node-gyp`, y exige una versión compatible de pnpr si se usa resolución remota.

**Por qué importa.** Si un repositorio utiliza registry corporativo y asume que una variable de entorno se expande, el fallback puede quebrar expectativas de procedencia de paquetes. Es una cuestión de integridad del proceso de instalación, aunque no demuestra que un proyecto concreto haya descargado paquetes indebidos.

**Qué hacer.** Buscar placeholders en `.npmrc` y `pnpm-workspace.yaml`; verificar el registry efectivo en CI y en desarrollo. Si se utiliza pnpm 11, evaluar 11.28.12. Confirmar antes compatibilidad con pnpr, si aplica.

**Qué ignorar.** No migrar de pnpm 11 a 12 únicamente por este arreglo. **Fuente:** [pnpm 11.28.12](https://github.com/pnpm/pnpm/releases/tag/v11.28.12).

### 3. P1 · Playwright 1.65.1: reparar una regresión antes de extender 1.65

**Qué cambió — 13/11, estable.** Playwright 1.65.1 corrige una regresión de 1.65 en clases decoradas con campos estáticos cuando `useDefineForClassFields` es `false`, además de ubicaciones de tests desplazadas una columna con Bun 1.4.4 o posterior.

**Por qué importa.** El briefing anterior ya analizó los cambios de 1.65 (reporters de fallos, elementos `inert` y campos TypeScript). El patch nuevo no justifica una migración por sí solo, pero evita introducir una regresión conocida si se actualiza.

**Qué probar.** Revisar `tsconfig` y Page Objects; ejecutar una suite representativa con 1.65.1, especialmente tests de formularios, overlays y clases decoradas. Mantener el informe completo disponible aunque se use `onlyFailures` para el feedback habitual.

**Qué ignorar.** Ejecutar el runner bajo Bun solo porque ahora esté soportado; no hay evidencia aquí de una ventaja en el proyecto. **Fuente:** [Playwright 1.65.1](https://github.com/microsoft/playwright/releases/tag/v1.65.1).

### 4. P2 · Vue 3.6 RC15: seguimiento, no migración

**Qué cambió — 12/11, pre-release.** Vue publicó 3.6.0-rc.15. La rama estable verificada sigue siendo 3.5.45 (5/11). El hecho de publicar otra RC no demuestra por sí solo una mejora que justifique cambiar producción.

**Por qué importa.** Vue 3.6 y Vapor siguen siendo dos decisiones separadas: validar la nueva versión del runtime no implica adoptar un modo de compilación distinto. Los frameworks UI y el tooling deben pasar pruebas de compatibilidad.

**Qué probar.** Mantener una rama experimental con tests de `watch`, `KeepAlive`, `Teleport`, formularios, transiciones y componentes UI. Comparar builds y diagnósticos, sin extrapolar benchmarks externos.

**Qué ignorar.** Migrar una SPA de negocio a RC15. **Fuente:** [Vue releases](https://github.com/vuejs/core/releases/tag/v3.6.0-rc.15).

## Deep dive · La reproducibilidad de dependencias es una capacidad de los agentes

Un agente que trabaja en un worktree puede instalar dependencias, cambiar versiones y ejecutar tests. Si el lockfile cambia entre instalaciones equivalentes o el entorno resuelve un peer diferente, el agente puede atribuir el fallo al código y empezar a modificar archivos que no tienen relación con el problema.

**Propuesta de política de ingeniería:**

1. Fijar el gestor y su versión mediante `packageManager` y los mecanismos soportados por el proyecto.
2. En CI, instalar siempre desde lockfile congelado y registrar runtime, versión de pnpm y configuración de registry, evitando secretos.
3. Para agentes, permitir instalaciones normales solo en worktrees de experimentación. Antes de entregar, exigir instalación congelada, typecheck, tests relevantes y build.
4. Si cambia `pnpm-lock.yaml`, explicar el motivo en la PR y comprobar que no cambió inesperadamente la resolución de peers.
5. Separar la evaluación del lockfile experimental v13 de cualquier actualización rutinaria.

**Ventajas:** menos diferencias entre worktrees, desarrolladores y CI; diagnósticos más fiables; menos tiempo perdido en falsos fallos. **Costes:** disciplina de versiones y un paso de verificación adicional. **Riesgo:** convertir el lockfile en un dogma y bloquear cambios legítimos de dependencias.

**Decisión:** probar pnpm 12.21 en un repositorio de laboratorio con varias dependencias peer; adoptar solo si la instalación y la CI se mantienen estables. No atribuir a pnpm problemas de CI sin reproducirlos.

## Radar de herramientas y prácticas

**1. Auditoría de procedencia de registries (práctica, no servicio).** Resuelve configuraciones que silenciosamente utilizan un origen distinto del previsto. Ventaja: barata, reproducible y especialmente útil en CI. Límite: comprobar configuración no sustituye auditoría de integridad ni SBOM. Alternativas: políticas de proxy corporativo, registries privados y escaneo de dependencias. **Experimento:** crear un proyecto sin secretos con registry deliberadamente inválido y verificar que la instalación falla de forma segura.

**2. Preparación offline de dependencias con `pnpm store add`.** Útil para entornos efímeros o aislados que necesitan instalar sin red. Ventaja: separar adquisición de paquetes de la fase de build. Límite: necesita preparar todas las dependencias y sus variantes de plataforma; no equivale a un build hermético completo. Alternativas: cachés de CI, mirrors internos o imágenes base preconstruidas. **Experimento:** preparar un proyecto pequeño y ejecutar una instalación offline congelada.

No se añaden plataformas nuevas sin una necesidad validada.

## Experimento recomendado (25 minutos)

**Hipótesis:** pnpm 12.21 evita cambios inesperados en resolución de peers en un monorepo pequeño.

1. **5 min:** crear un worktree de laboratorio y registrar `node -v`, `pnpm -v` y el hash del lockfile.
2. **5 min:** instalar con pnpm 12.21 y repetir la instalación sin modificar manifests.
3. **5 min:** comprobar que no cambia el lockfile ni la resolución de peers.
4. **5 min:** ejecutar `pnpm install --frozen-lockfile`, build y Vitest.
5. **5 min:** documentar resultados y decidir si conviene actualizar el baseline.

**Éxito:** instalación repetible, cero cambios inesperados en lockfile y tests verdes. **Fracaso:** cualquier diferencia de peers o lockfile sin causa explicable.
